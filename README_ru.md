# TG Story Watcher

Самостоятельно размещаемое (self-hosted) веб-приложение для мониторинга и
автоматического просмотра **Telegram Stories** через официальный
**Telegram MTProto User API** (Telethon). Поддерживает несколько локальных
пользователей: у каждого свои аккаунты Telegram, теги, настройки поиска,
правила, очереди, история и аналитика.

> ⚠️ Приложение работает только с **официальным протоколом Telegram MTProto**,
> использует один аккаунт — одну сессию и **никогда не пытается обходить
> лимиты или антиспам**. Все действия по просмотру выполняются последовательно,
> с задержками, паузами и проверками безопасности — чтобы защитить ваш аккаунт
> от блокировки.

## Возможности

- **Однопараметровая конфигурация** — задайте только «Просмотров в сутки»
  (50–12 000); все остальные технические параметры вычисляются автоматически
- **Адаптивный поиск историй** — частота и количество результатов подстраиваются
  под заполненность очереди, чтобы просмотры распределялись равномерно в течение суток
- **Локальная регистрация** — вход по имени, email и паролю; пароли хранятся
  в формате PBKDF2 (открытым текстом не сохраняются)
- **Мультипользовательность** — несколько пользователей, данные изолированы по
  авторизованному пользователю
- **Подключение Telegram MTProto** — номер телефона → код → опционально 2FA
- **Несколько Telegram-профилей** на одного пользователя приложения
- **Автоматическая синхронизация профиля** — имя, фамилия, юзернейм, телефон, Telegram ID
- **Мониторинг и автопросмотр** доступных Stories с фильтрацией
- **Белый и чёрный списки** авторов, пользовательские теги и правила
- **Discovery** — поиск по хэштегам, местам и георадиусу, карта собранных мест
- **Очередь просмотров** — приоритеты, отмена, повтор, лимиты скорости
- **Панель управления** с графиками и историей действий
- **Аналитика аккаунтов** — свои активные/архивные Stories, просмотры, реакции,
  пересылки, ER, списки зрителей, снимки по времени, лучшие Stories, фильтры по периодам
- **Адаптивный веб-интерфейс** с тёмной/светлой темой и переводами (EN/RU)
- **Поддержка VPN-прокси** — встроенный Xray SOCKS5 прокси для Telegram MTProto
  с управлением серверами через подписку, автоматическим переключением и
  мониторингом изменений IP
- **Развёртывание через Docker Compose** — PostgreSQL, Redis, VPN (Xray), воркер, фронтенд, Nginx
- **Самовосстановление** — воркер перезапускается при зависании, застывшие задачи
  очереди восстанавливаются автоматически, у всех сервисов есть healthcheck

## Как это работает

```
Браузер
   │
   ▼
Nginx ───────────────────► Next.js фронтенд (страницы UI)
   │
   ▼
FastAPI бэкенд ──────────► PostgreSQL (данные) + Redis (кэш)
   │
   ├── Единый фоновый процесс (worker)
   │   ├── Планировщик (синхронизация Stories, аналитика)
   │   ├── Очередь просмотров (задержки, лимиты скорости, восстановление задач)
   │   ├── Контроллер discovery (адаптивный поиск, ротация гео/хэштегов)
   │   └── Монитор VPN IP (отслеживание смены IP → переподключение клиентов)
   │
   └── VPN-контейнер (Xray SOCKS5)
       └── Маршрутизация трафика Telegram MTProto через прокси-туннель
```

Один процесс `worker` совмещает синхронизацию, очередь, discovery и аналитику,
потому что файлы Telethon-сессий нельзя безопасно открывать из нескольких
процессов. Бэкенд (FastAPI) отдаёт REST API и в реальном времени обновляет
очередь просмотров; воркер забирает задачи, авторизуется в Telegram как
подключённый аккаунт и выполняет просмотры с учётом всех лимитов.

Опциональный VPN-контейнер запускает Xray SOCKS5 прокси, который
маршрутизирует трафик Telegram MTProto через удалённый сервер. При смене
внешнего IP VPN (например, переподключение к другому серверу) воркер
проактивно отключает всех клиентов Telegram до возникновения
`AuthKeyDuplicatedError`.

## Авто-конфигурация

Вся система строится вокруг **одного** пользовательского параметра —
«Просмотров в сутки»:

```
            ПРОСМОТРОВ В СУТКИ
                    │
                    ▼
             основной лимит
                    │
    ┌───────────────┼────────────────┐
    ▼               ▼                ▼
скорость        поиск            очередь
просмотров
    │               │                │
    ▼               ▼                ▼
в час / минуту  интервал       параллельность
    │               │                │
    └───────────────┼────────────────┘
                    ▼
            задержки просмотра
                    ▼
          равномерная работа
              в течение суток
```

### Вычисляемые параметры

| Параметр | Формула | Пример (12 000/сутки) |
|---|---|---|
| Просмотров в час | `daily / 24` | 500 |
| Просмотров в минуту | `ceil(daily / 1440)` | 9 |
| Мин. задержка | `max(3, min(20, avg_delay × 0.3))` | 3с |
| Макс. задержка | `max(10, min(120, avg_delay × 1.5))` | 11с |
| Параллельность очереди | по дневному лимиту (1–4, жёсткий потолок 4) | 3 |
| Интервал мониторинга | `max(15, min(60, 120 - daily/100))` | 15с |
| Интервал поиска | адаптивно по заполненности очереди | 60–600с |
| Результатов за поиск | адаптивно по «разрыву» очереди | 10–200 |

> Значения `parallel` и `max_tasks` дополнительно ограничиваются жёсткими
> потолками в воркере, чтобы не исчерпать пул соединений к БД и не заблокировать
> event loop (защита от «зависания» очереди).

### Адаптивный поиск (discovery)

Система непрерывно отслеживает состояние очереди и корректирует:

- **Очередь пуста** → поиск каждые 60 секунд, максимальное количество результатов
- **Очередь наполовину** → поиск каждые 5 минут, умеренное количество
- **Очередь полная** → поиск каждые 10 минут, минимальное количество
- **Очередь переполнена** → поиск прекращается
- **Просмотры почти исчерпаны** → поиск прекращается

### Защита дневного лимита

Дневной лимит — абсолютный потолок. Перед каждым просмотром проверяется:

```
if просмотрено_сегодня >= лимит_в_сутки:
    СТОП
```

Лимит отслеживается по аккаунту в день; при достижении — аккаунт
приостанавливается. Изменение лимита в течение дня корректирует остаток:

```
До: лимит 5000, просмотрено 3000
После установки 12000: осталось 9000
```

## Требования

**Для запуска через Docker (рекомендуется):**

- Docker и Docker Compose v2 (входят в Docker Desktop / docker-ce)
- API-учётные данные Telegram (`TELEGRAM_API_ID`, `TELEGRAM_API_HASH`) —
  получить на https://my.telegram.org
- Аккаунт Telegram для авторизации MTProto

**Для ручного запуска (режим разработки):**

- Python 3.12+
- Node.js 18+ и npm
- PostgreSQL 16 (или SQLite для быстрого старта без Postgres)
- Redis 7

## Установка через Docker (рекомендуется)

### 1. Получить код

```bash
git clone https://github.com/devlewicki/TG-Story-Watcher.git
cd TG-Story-Watcher
```

### 2. Настроить окружение

```bash
cp .env.example .env
```

Отредактируйте `.env`. **Обязательно** задайте Telegram API-учётные данные:

```dotenv
TELEGRAM_API_ID=12345678
TELEGRAM_API_HASH=ваш_api_hash

# Сгенерируйте надёжные значения (продакшн):
#   python -c "import secrets; print(secrets.token_urlsafe(32))"
SECRET_KEY=ваш_секретный_ключ
STORYWATCHER_API_TOKEN=ваш_токен

# Опционально: VPN-прокси для Telegram MTProto
# TELEGRAM_PROXY_ENABLED=true
# TELEGRAM_PROXY_HOST=vpn
# TELEGRAM_PROXY_PORT=1080
# VPN_SUBSCRIPTION_URL=https://ваша-url-подписки-v2ray
```

### 3. Собрать и запустить

> Первая сборка фронтенда занимает несколько минут.

```bash
docker compose up -d --build
```

Проверить состояние:

```bash
docker compose ps
```

Все сервисы должны перейти в статус `healthy` (healthcheck у каждого контейнера).

### 4. Открыть приложение

| Что | URL |
|---|---|
| Веб-интерфейс | http://localhost:8081 |
| Веб-панель (внешний порт) | `WEB_PORT` в `.env` (по умолчанию `8081`) |
| Backend API | http://localhost:9000/api |
| Интерактивная документация API | http://localhost:9000/docs |

Контейнеры:

| Контейнер | Назначение |
|---|---|
| `vpn` | Xray SOCKS5 прокси (vmess/vless/shadowsocks/trojan) с авто-фейловером |
| `postgres` | PostgreSQL 16 — база данных |
| `redis` | Redis 7 — кэш |
| `backend` | FastAPI REST API (порт 9000, только внутри сети) |
| `worker` | Единый фоновый процесс: синхронизация + очередь + аналитика + discovery + VPN монитор |
| `frontend` | Next.js SSR — веб-интерфейс (порт 3000, только внутри сети) |
| `nginx` | Обратный прокси, открывает наружу порт 8081 |

### Обновление

```bash
git pull
docker compose up -d --build
```

Данные (PostgreSQL `postgres_data` и сессии Telegram `sessions_data`) хранятся
в Docker-томах и сохраняются при пересборке.

### Остановка и удаление

```bash
docker compose down        # остановить, данные сохраняются
docker compose down -v     # остановить И удалить все данные (осторожно!)
```

### Логи и бекапы

```bash
docker compose logs -f worker
docker compose logs --tail=200 backend
docker compose logs -f vpn

# Бекап PostgreSQL
docker compose exec postgres pg_dump -U storywatcher storywatcher > backup.sql

# Восстановление
cat backup.sql | docker compose exec -T postgres psql -U storywatcher -d storywatcher
```

Сессии Telegram лежат в томе `sessions_data` (`SESSIONS_DIR=/data/sessions`) —
сделайте его резервную копию вместе с базой для полного восстановления.

## Ручной запуск (режим разработки)

Docker — основной и рекомендуемый способ развёртывания (воркер, очередь и
healthcheck настраиваются в `docker-compose.yml`). Для локальной разработки
проект также можно запустить вручную.

### Бэкенд (FastAPI)

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate       # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Быстрый старт на SQLite (без Postgres):

```bash
export DATABASE_URL="sqlite:///./data/storywatcher.db"
export REDIS_URL="redis://localhost:6379/0"
export TELEGRAM_API_ID=...
export TELEGRAM_API_HASH=...
uvicorn app.main:app --reload --port 9000
```

Или с локальным PostgreSQL:

```bash
export DATABASE_URL="postgresql+psycopg2://storywatcher:storywatcher@localhost:5432/storywatcher"
uvicorn app.main:app --reload --port 9000
```

### Фронтенд (Next.js)

```bash
cd frontend
npm install
npm run dev
```

Фронтенд: http://localhost:3000 — Next.js проксирует `/api` на бэкенд
(http://localhost:9000), проблем с CORS нет.

### Воркер

```bash
cd backend
python -m app.workers.combined
```

> ⚠️ Не запускайте несколько воркеров, работающих с одними и теми же файлами
> Telethon-сессий — SQLite-сессии не могут безопасно использоваться
> несколькими процессами одновременно.

| `VPN_IP_CHECK_INTERVAL` | `30` | Как часто монитор VPN IP проверяет смену IP (секунды) |

### Безопасность в продакшене

- Смените `SECRET_KEY` и `STORYWATCHER_API_TOKEN` — при изменении `SECRET_KEY`
  все пользователи будут автоматически разлогинены (токены входа подписываются им).
- Смените `POSTGRES_PASSWORD` на надёжный.
- Не коммитьте `.env`, файлы сессий и `node_modules` (покрыто `.gitignore`).
- Рекомендуется запуск за обратным прокси с HTTPS (пример конфига для
  Nginx/Caddy — в [CONTRIBUTING.md](CONTRIBUTING.md#reverse-proxy-nginxcaddy)).

## Использование

1. **Регистрация.** Откройте приложение → зарегистрируйтесь
   (имя, фамилия, email, пароль).
2. **Вход.** Введите email и пароль.
3. **Подключение Telegram.** Аккаунты → Добавить аккаунт → номер телефона →
   код из Telegram → пароль 2FA, если потребуется.
4. **Проверка.** Карточка аккаунта покажет имя, юзернейм, телефон и Telegram ID.
5. **Настройка.** Установите «Просмотров в сутки» (Настройки → Лимиты).
   Остальные параметры вычисляются автоматически.
6. **Источники.** Поиск историй → добавьте хэштеги, места или включите
   гео-радиус поиска.
7. **Мониторинг.** Включите мониторинг для подключённых аккаунтов — воркер
   начнёт обнаруживать и просматривать Stories автоматически.
8. **Аналитика.** Страница «Аналитика» — просмотры, реакции, пересылки, ER
   и списки зрителей ваших Stories.
9. **Управление.** Белый/чёрный списки для контроля авторов; «Очередь» —
   отслеживание и управление задачами (отмена, повтор).

> авторизовал. Один и тот же аккаунт Telegram не может быть привязан
> к другому пользователю.

## Статусы аккаунтов и очереди

**Аккаунты:** `ACTIVE` — работает, `PAUSED` — приостановлен (в т.ч. при
достижении дневного лимита), `FLOOD_WAIT` — Telegram ограничил скорость
(авто-пауза), `ERROR` — ошибка, `DISCONNECTED` — требуется переподключение,
`AUTH_REQUIRED` — нужна авторизация, `BANNED_OR_RESTRICTED` — ограничен Telegram.

**Очередь:** `PENDING` — ждёт обработки, `PROCESSING` — выполняется,
`VIEWED` — просмотрено, `SKIPPED` — пропущено, `FAILED` — ошибка (повтор через
API), `CANCELLED` — отменено.

Задачи, «зависшие» в `PROCESSING` (после падения/перезапуска воркера), автоматически
восстанавливаются: сначала возвращаются в `PENDING` и пробуются снова, при
исчерпании авто-повторов переводятся в `FAILED` для ручной обработки.

## Безопасность и лимиты Telegram

Telegram может накладывать ограничения на аккаунты, выполняющие слишком много
автоматических действий. Приложение обрабатывает это корректно:

- Чрезмерный просмотр может вызвать статус `FLOOD_WAIT` — воркер отступает,
  а не повторяет запросы в цикле
- Лимиты скорости автоматически вычисляются из «Просмотров в сутки»
- Просмотры распределяются равномерно в течение дня
- Дневной лимит проверяется **перед каждым** просмотром и никогда не превышается
- Белый список исключается при создании очереди и перепроверяется перед действием
- Чёрный список авторов всегда пропускается
- Транзиентные сетевые ошибки повторяются с экспоненциальной задержкой
- После перезапуска сервера очередь автоматически возобновляется

> Превышение безопасных лимитов — на ваш страх и риск. Telegram может
> ограничить или заблокировать аккаунты с «ботоподобным» поведением.

## VPN и поддержка прокси

Приложение включает встроенный VPN-контейнер для маршрутизации трафика
Telegram MTProto через удалённый прокси-сервер. Это полезно когда:

- Telegram заблокирован в вашем регионе
- Вам нужно маршрутизировать трафик через определённую страну
- IP вашего сервера ограничен Telegram

### Поддерживаемые протоколы

VPN-контейнер работает на [Xray](https://xtls.github.io/) и поддерживает
конфигурации на основе подписок со следующими протоколами:

- **VMess** (с транспортами TLS, WebSocket, gRPC)
- **VLESS** (с транспортами TLS, Reality, WebSocket, gRPC, xhttp)
- **Shadowsocks** (SIP002 и legacy формат)
- **Trojan**

### Как это работает

1. VPN-контейнер загружает вашу подписку V2Ray при старте
2. Парсит все ссылки на серверы и проверяет каждого кандидата на выделенном порту сканирования
3. Выбирает самый быстрый рабочий сервер и запускает Xray как SOCKS5 прокси
4. Контейнер `worker` маршрутизирует трафик Telegram через SOCKS5 прокси
5. **Монитор VPN IP** непрерывно проверяет внешний IP — при его смене
   (например, переподключение VPN к другой стране) все клиенты Telegram
   проактивно отключаются для предотвращения `AuthKeyDuplicatedError`

### Фейловер

- Периодические проверки здоровья туннеля каждые `VPN_PROBE_INTERVAL` секунд
- После `VPN_FAIL_THRESHOLD` подряд идущих неудач VPN-контейнер сканирует
  всех кандидатов в подписке и переключается на самый быстрый рабочий сервер
- Период охлаждения предотвращает чрезмерное повторное сканирование
- Рабочий SOCKS5 порт никогда не отключается во время сканирования — заменяется
  только после проверки работоспособности замены

### Включение VPN

1. Установите `VPN_SUBSCRIPTION_URL` в `.env` на URL подписки V2Ray
2. Установите `TELEGRAM_PROXY_ENABLED=true`
3. Установите `TELEGRAM_PROXY_HOST=vpn` и `TELEGRAM_PROXY_PORT=1080`
4. Пересоберите: `docker compose up -d --build`

VPN-контейнер будет автоматически включён в стек compose.

## Производительность

- **Графики дашборда** — агрегированные запросы (`EXTRACT(HOUR)`, `DATE()`)
  вместо десятков отдельных `COUNT(*)`
- **Список Stories** — `LEFT JOIN` и `OFFSET/LIMIT` на уровне БД
- **Аналитика** — подсчёт зрителей одним `COUNT(*)`
- **Кэш настроек** — `compute_all_from_daily()` через LRU
- **Пул соединений PostgreSQL** — `pool_size=10`, `max_overflow=20`,
  `pool_timeout=10с`, `pool_recycle=1800с`
- **Аналитика архивов** — выполняется редко (по умолчанию раз в час), чтобы
  не забивать Telegram RPC-запросами во время просмотров
- **Воркер очереди** — таймауты на каждую задачу не позволяют одному
  зависшему RPC блокировать всю очередь; DB-сессии открываются внутри
  семафора для исчерпания пула

## Безопасность

### Аутентификация

- **Локальная регистрация** — хеширование паролей PBKDF2-SHA256 (310k итераций)
- **Токены** — `user.<base64 payload>.<hmac signature>` с 30-дневным сроком
  действия, проверяемые по HMAC через `SECRET_KEY`
- **Отзыв токенов** — токены можно отозвать через хранилище настроек
- **Изоляция пользователей** — все эндпоинты привязаны к `user_id`
  авторизованного пользователя; кросс-пользовательский доступ заблокирован
  на уровне API

### Защита эндпоинтов

- Эндпоинты пользовательской авторизации (`/api/user-auth/*`) — регистрация и вход
- Эндпоинты Telegram авторизации (`/api/auth/*`) — требуют валидный пользовательский токен
- Эндпоинты аккаунтов, stories, очереди, аналитики и настроек требуют
  аутентификации через заголовок `X-API-Token`
- Проверка работоспособности (`/api/health`) — единственный эндпоинт без авторизации

- Смените `SECRET_KEY` и `STORYWATCHER_API_TOKEN` для продакшена

- Запускайте за HTTPS-обратным прокси (Nginx/Caddy)

## Надёжность и самовосстановление

### Watchdog воркера

- Воркер записывает heartbeat-файл каждый цикл
- Если нет прогресса в течение `WORKER_STALL_TIMEOUT` секунд, воркер завершается
- Политика `restart: unless-stopped` в Docker перезапускает его автоматически
- После `WORKER_MAX_ERRORS` подряд идущих ошибок цикла воркер завершается

### Восстановление очереди

- Задачи, застрявшие в `PROCESSING` (например, после сбоя), автоматически
  возвращаются в `PENDING` и повторяются
- Таймауты на каждую задачу (`asyncio.wait_for`) не позволяют одному
  зависшему RPC блокировать очередь
- Задачи с истёкшим таймаутом возвращаются в `PENDING` с задержкой 30 секунд
  или переводятся в `FAILED` при исчерпании бюджета авто-повторов

### Устойчивость VPN

- VPN-контейнер проверяет здоровье туннеля и переключается на запасные серверы
- Монитор VPN IP определяет смену IP и проактивно отключает клиентов
  Telegram для предотвращения `AuthKeyDuplicatedError`
- После смены IP клиенты Telegram переподключаются автоматически в следующем цикле

### Healthchecks

| `postgres` | `pg_isready` | 5с |

| `backend` | HTTP `/api/health` | 15с |
| `worker` | Проверка heartbeat-файла | 15с |
| `frontend` | `fetch()` на порту 3000 | 15с |
| `nginx` | `wget` на порту 80 | 15с |
| `vpn` | `curl` через SOCKS5 | 20с |

## Тестирование

Интеграционные тесты на pytest + SQLite in-memory (PostgreSQL не требуется):

```bash
cd backend
pip install pytest httpx
python -m pytest tests/ -v
```

Тесты покрывают: пагинацию и сортировку Stories, агрегированные графики
дашборда, статистику, аналитику (зрители/периоды/лучшие Stories), кэширование
`compute_all_from_daily()` и изоляцию словарей ротации discovery.

## Устранение неполадок

| Проблема | Решение |
|---|---|
| Контейнеры не стартуют / в рестарте | `docker compose ps` и `docker compose logs --tail=200 backend worker`. Проверьте API-ключи Telegram в `.env` |
| Код Telegram не приходит с первого раза | `docker compose logs --tail=200 backend`. Поток входа пересоздаёт клиент при ошибках. Подождите и запросите новый код |
| Просмотры не идут / очередь застряла | Проверьте статус аккаунта и воркера: `docker compose ps`, `docker compose logs --tail=200 worker`. Зависшие `PROCESSING` восстанавливаются автоматически |
| Воркер «завис» (healthcheck healthy, но логов нет) | Новый воркер сам завершается после `WORKER_STALL_TIMEOUT` без прогресса — контейнер перезапустится. Перезапустите вручную: `docker compose restart worker` |
| Профиль Telegram не отображается | Обновите страницу «Аккаунты» после авторизации |
| Пользователь видит чужие данные | Выйдите, очистите хранилище сайта, войдите заново. Не копируйте токен между профилями |
| `FLOOD_WAIT` на аккаунте | Нормально — Telegram ограничил скорость. Воркер отступает автоматически |
| `AuthKeyDuplicatedError` | Сменился IP VPN и клиенты были переподключены. Если повторяется — проверьте логи VPN: `docker compose logs vpn` |
| Порт 8081 занят | Смените `WEB_PORT` в `.env` |
| Фронтенд показывает старый интерфейс | Обновите страницу (Ctrl+Shift+R) |
| VPN не подключается | Проверьте `docker compose logs vpn`. Убедитесь, что `VPN_SUBSCRIPTION_URL` установлен и подписка валидна |
| VPN часто переключается | Проверьте подписку на наличие рабочих серверов. Увеличьте `VPN_FAIL_THRESHOLD` для снижения чувствительности |
| Смена IP VPN вызывает проблемы | Монитор VPN проактивно отключает клиентов при смене IP. Проверьте `docker compose logs worker` на предмет логов переподключения |
